Writing a frontend

A frontend holds a Session, renders its view data, and turns what users do into commands. These are the patterns BrewQuiverTerm follows, and that a graphical frontend can follow too.

Rendering

  • Draw from node_summaries, arrow_summaries and positions, never from the quiver directly: they carry what changed, what is selected, the warnings and the colors.
  • Get the quiver with quiver(s) each time: undoing a structural edit restores a snapshot, which replaces it.
  • Highlight changed(s) after every step; show status(s) and the count of warnings(s) in a status bar, with undo_description(s) for the Undo menu.

Selection

Keep the cursor in the session: select!(s, NodeRef(:kettle)), and select!(s, Add(), ref) for a click with shift. Undo and redo restore it, a renamed node keeps it, and removed items leave it.

Editing

a number boxparse each change with parse_value and apply it (SetAmount, SetArrowField, SetEquipmentField); the edits merge into one step

dragging a nodebegin_transaction!, a MoveNode per frame, commit! on release, abort! on Escape

a refused editshow the message of the CommandError: the session is unchanged
quitting, openingask when isdirty

Data of the frontend

Keep what only your frontend needs in the nodeviews under your prefix ("app.size", "term.folded"), set with SetView so that it is undoable and saved with the quiver; propose new unprefixed keys for the convention in this package.

Engine additions

What is useful outside any interface belongs in BrewQuiver: propose it there, and wrap it here in a command.
