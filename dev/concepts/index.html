Concepts

The session

A Session is what an interface edits: a quiver of BrewQuiver, the path of its file, the models it is brewed with, and

  • its latest brew (result), kept up to date after every edit by rebrew! from the nodes the edit affected, falling back to a whole brew;
  • the state of the brew (status): Brewed, or BrewFailed for a quiver loaded in a state that does not brew;
  • the nodes whose results changed in the last step (changed): those whose contents or leftover differ from the previous brew, for interfaces to highlight;
  • the warnings of the brew (vessels overfilled; what BrewQuiver logs, e.g. when importing a recipe, collected rather than printed);
  • the selection: nodes (NodeRef) and arrows (ArrowRef), the last being the primary one;
  • the History of the edits;
  • a library of ingredients to add.

Sessions are made with Session, open_session (a file of a quiver) or import_recipe (a BeerJSON recipe), and saved with save!.

Commands

Interfaces change the quiver only through commands, EditCommands applied with apply!. A command is a plain value: SetAmount(:pale, 4.8u"kg"), Connect(:hops => :kettle, Transfer(20u"g"; remaining = 10u"minute")). Each one

  • validates itself, and BrewQuiver checks the rules of the quiver (no cycles, a transformation alone, one drain) before changing anything: a refused command throws a CommandError and leaves the session as it was;
  • knows the nodes it affects, from which the brew is updated;
  • describes itself ("Set :pale to 4.8 kg"), for menus and history lists;
  • records what reverts it exactly, before it is applied: an Inverse command (set back the old amount) or a Snapshot of the whole quiver, for the edits whose inverse would be error-prone (removing a node with its arrows in their order).

An edit after which a quiver that brewed no longer brews (a drain with not enough liquid, a fermentation without yeast) is refused too, and reverted: the quiver of a session always brews, unless it was loaded broken, in which case it can be edited until it brews.

Layout-only commands (MoveNode, SetView) keep the brew.

History

The History of a session has an undo and a redo stack of steps. A step is a command, several grouped in a transaction (a node dragged across many frames, a form, a paste), or several merged (the same field typed into, within a short window). Undo reverts a step with its records and restores the brew and the selection; redo applies its commands again. A saved marker tells whether the session has unsaved changes, also after undoing back to the saved state. The history lives in memory only: it is not written to the files.

View data

Frontends render plain data, with Unitful quantities: NodeSummary (the results of a node, its display color, its warnings, whether it changed or is selected), ArrowSummary, node_detail, results_table, timeline_rows, vessel_bookings, solution_rows, and the fields of arrows and equipment for forms. format shows a quantity with the decimals of its unit, and parse_value reads back what users type.

Layout and the nodeview convention

nodeview(q, label) of BrewQuiver is a dictionary of free data for interfaces, kept in the files of quivers. All frontends use these keys:

keyvaluemeaning
"position"[x, y], numbersposition in abstract layout units: one per layer (x, downstream) and per slot (y, downwards)
"collapsed"Boolthe node is shown collapsed
"color""#rrggbb"a color chosen by the user, overriding that of the beer
"note"Stringa note of the user about the node

A frontend keeps its own data under its prefix: "term." for BrewQuiverTerm, "app." for BrewQuiverApp. SetView checks the keys without a prefix against this convention. layout computes positions in these units, and positions gives the stored ones or the computed ones for the nodes without.
